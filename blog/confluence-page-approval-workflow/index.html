Confluence page approval: how to set up a review and sign-off workflow

Policies, procedures and release notes often need a named person to approve them before they count. In audits (ISO 27001, SOC 2, GxP) you also need to show who approved which version, and that nobody changed the page afterwards. Here is what Confluence Cloud gives you, and where it stops.

What Confluence offers on its own

  • Page status (for example "In progress", "Ready for review", "Verified"). This is a label anyone with edit rights can set. It does not record an approver and does not reset when the page changes.
  • Restrictions: you can limit who may edit a page, which keeps drafts safe but is not an approval.
  • Comments and @mentions: reviewers can say "approved" in a comment. That works for small teams, but there is no overview and no link to the version that was approved.
  • Page history: shows every version, but you have to match versions to approvals yourself.
  • Native Approvals (beta, Premium and Enterprise only): Atlassian is rolling out built-in page approvals on the higher plans. They require every approver to sign off (there is no "any one of them" option), and they are not available on Free or Standard. If you are on Premium, try them first.

What an approval workflow needs

  1. Named approvers, with a rule: everyone must approve, or any one of them.
  2. A visible status on the page: pending, approved, changes requested.
  3. Approval tied to a version: if the page changes after approval, the approval is no longer valid.
  4. An audit trail: who decided, when, on which version, with their comment.
  5. An overview: what is waiting for me, and what is outdated.

Setting it up with Page Approval for Confluence

Page Approval for Confluence adds exactly these pieces on any Confluence plan, including Standard:

  1. Open a page and choose Request approval next to the author name.
  2. Pick the approvers, choose all or any, and optionally set a due date. Approvers are notified through normal Confluence @mentions.
  3. Approvers approve or request changes right on the page, with a comment.
  4. The status shows next to the author: Approval pending 1/2, Approved v5 or Changes requested.
  5. When someone publishes v6, the page shows Approval outdated. If the page changes during a review, earlier decisions are reset, so nobody approves text they haven't seen.
  6. Each space gets an Approvals page with a "Waiting for me" list and every request with its full history.

Status labels also work in Confluence search and CQL, so you can build a report of every approved, or outdated, policy page.

Tips for audits

  • Use default approvers per space (for example the policy owner) so nobody forgets to add them.
  • Before an audit, search for Approval outdated to find pages that changed since sign-off.
  • Use the space's Approvals page as evidence of review: every decision is listed with its page version.
